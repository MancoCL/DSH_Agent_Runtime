Fix the scope trap: gac_scope was refused by its own gate

Found by running the gate in a live session, not by this suite. With a scope
declared, gac_scope was unclassified, so the guard refused it with
GAC_UNGUARDABLE_WRITE_DENIED - meaning the scope could not be inspected,
re-declared, or released. Declaring a scope was a one-way trap.

gac_scope only mutates an in-memory registry and touches no file, so it is now
classified as such. Added four regression tests, including the empty-scope case
where every write is refused and the scope tool is the only way out.

Phase 0 is now verified end to end in a live session: an in-scope write was
created, an out-of-scope write was refused with GAC_WRITE_SCOPE_DENIED, and a
shell write was refused with GAC_SHELL_DENIED_UNDER_SCOPE. The decisive check is
the filesystem: neither refused path existed afterwards. Refusal happens before
dispatch, which is the assumption the architecture rests on.

README records the verification, and states the general rule the defect teaches:
any tool whose enforcement path is itself guarded must be provably unable to
write, or it recreates this deadlock.

144 tests pass. HMR reload confirmed: a lib/ edit reloaded the plugin within
seconds, so no restart is needed for code changes.
