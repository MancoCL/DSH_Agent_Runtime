# ADR-0001：节点执行载体 —— 用原生子会话，而不是自造执行器，也不是 Agent Teams

状态：**待用户确认**（阶段 0 产出；本 ADR 通过之前不写 `lib/`）
日期：2026-10-05
范围：`dsh-gac-runtime` 的「派遣」到底由谁执行

## 1. 问题

`lib/executor.js` 的 `createSessionExecutor()` 是**占位**：它把节点置为 `in_progress` 就返回，
真正的执行落回主会话——由模型自己干完，再手工 `report`。后果是今天四轮活体验证反复暴露的同一件事：

- 「独立验证」在事实层面从未成立（Builder 与 Verifier 是**同一个会话**，只是 prompt 不同）；
- 「并行批次」只是协调器算出来的批次，执行侧串行；
- `dispatch_id` 与结果之间没有真正的执行者，只有自觉。

所以本 ADR 要定的不是「再加一条规则」，而是**执行载体换谁**。

## 2. 候选与实测/源码证据

宿主里有三个候选，**不是三个并列的工具，而是「同一基座 + 两个消费者」**：

```text
① 原生接缝   ctx.subagents（start / startContinuable / sendMessage / interrupt / listChildren）
              └─ 内部经 ctx.agents.create() / resume() 真正建子会话
②a 一次性消费者 dsh-tool-subagent（subagent / subagent_fork 工具）
②b 团队消费者   dsh-experimental-agent-team + dsh-experimental-tool-agent-team
                （spawn_teammate / send_message / wait_agent / team_task_* / list_agents）
③ 进程内     ctx.llm.stream（同会话内的另一次模型调用）
```

| 属性 | ① `ctx.subagents` | ②a `subagent` 工具 | ②b Agent Teams | ③ 进程内 `llm.stream` |
| --- | --- | --- | --- | --- |
| 独立 session identity | ✅ `SubagentRun.id: SessionId` | ✅ | ✅（`childId: SessionId`） | ❌ |
| 独立 context / messages | ✅ | ✅ | ✅ | ❌ |
| 独立工具面 | ✅ **`SubagentStartRequest.toolFilter`**（+ `persona`） | ✅ | ✅ | ❌ |
| 独立写作用域 | ✅（按子会话 id 声明） | ✅ | ✅ | ❌ |
| 结构化结果回传 | ✅ `result: Promise<SubagentResult>` + `outputSchema` | ✅（回调用方） | ⚠️ 消息/看板，非结构化 | ✅ |
| 取消 | ✅ `signal` + `subagents.interrupt(id, authority)` | 有限 | ⚠️ `interrupt_agent` | ✅ |
| 深度限制（防递归委派） | ✅ `maxDepth` + `SubagentDepthError` | — | — | — |
| 跨轮 / 可寻址 | continuable 模式（`startContinuable`） | ❌ **实测**：`send_message` 报 `active teammate not found` | 声称可以；**实测**：inactive 唤不醒 | — |

| 成熟度 | 稳定（普通包） | 稳定 | **experimental** | 稳定 |

证据索引见 §7。

## 3. 决定

**D1（基座）**：节点执行载体 = **`ctx.subagents.start(providerName, request)`**；需要跨轮时才用
`startContinuable(spec)`。GAC 只负责：policy、routing、context contract、authority、acceptance。
DSH 负责：agent/session 生命周期、传输、模型调用、工具执行、取消。

**D2（不造新运行时）**：不建 worker pool / daemon / queue / RPC / 进程监督。

**D3（团队功能的位置）**：Agent Teams **不作为执行基座、也不作为任务模型**，只作为**可选交互面**：
「必须跨轮、需要人在环、需要多会话协作」的节点可以挂到 Team 上，但 GAC 的任务记录始终是唯一事实
来源（Team 看板只做投影）。理由：`team_task_*` 没有 mode / 写作用域 / 证据 / 验证计划 / 风险升级，
两套任务模型必然漂移；且它今天在「唤起居留成员」上是失败的。

**D4（角色工具面）**：角色工具面靠 **`SubagentStartRequest.toolFilter`**（必要时加 `persona`）
在**子会话创建时**装进子会话自己的 ctx，因此子会话**第一次装配**的工具清单里就没有
`write`/`edit`/委派类工具。`tools.restrict` 与 `tools/pre-execute` 守卫降为第二、第三层防线。

**D5（结果契约）**：子会话结果用 `outputSchema` 约束成结构化产物（node 的 status/summary/artifacts），
然后交给 `applyResult()`；不再从散文里猜。

## 6. 风险、止损与回滚

| 风险 | 表现 | 处置 |
| --- | --- | --- |
| 自锁（第三种形态） | 子会话继承了父的管辖/收权 → 子会话写不了它该写的文件 | 子会话有自己的 session id：写作用域与收权**按子会话 id 单独声明**；父会话在子会话在飞期间必须仍能正常用工具（列为阶段 1 的 DoD） |
| 递归委派绕过角色边界 | 只读角色通过 `subagent`/`spawn_teammate` 再开一个不受限的子会话 | `toolFilter` 把委派类工具一并 deny + `maxDepth` 限制；守卫作为第二层 |
| 结果不可靠 | 子会话只回散文，GAC 无法判定 | `outputSchema` 强制结构化；无 schema 不放行 |
| Provider 缺席 | 本机没注册 provider → `list()` 为空 | 保留 session executor 作为**显式降级**（`mode: 'session-fallback'` 写进加载报告与结果），绝不静默 |
| preset 来源不在运行期 | 角色 preset 需要改 profile 配置（+重启） | **不需要**：D4 用 `toolFilter` 就够；preset 只沿用继承来的 composed preset。若将来要真正的预设级角色，再单独立项 |
| 平台不支持真并发 | 两个子会话无法真正并行 | 记为平台限制，**不**把「逻辑并行」写成「实际并行」 |

**止损条件**：阶段 1 若出现「子会话创建需要改 profile 配置且必须重启才能生效」，则把 native 派遣
降级为可选开关（默认关），并先把结论写进 CUTOVER §6 再继续。

## 8. 阶段 1 的最小竖切（待本 ADR 确认后开工）

1. `lib/child-executor.js`：`ctx.inject(['subagents'])` → `list()` 选 provider →
   `start(provider, { label: '<task>/<node>', prompt, parent: exec.agent, signal, toolFilter, outputSchema, maxDepth })`
   → `await run.result` → `applyResult(task, { node_id, dispatch_id, status, result_ref/artifacts })`；
   失败/异常按 `failed`/`blocked` 回灌；`dispose()` 在 finally。
2. `lib/executor.js`：`implementation` 且 `write_scope` 非空 → 走 child executor；**没有 provider 时**
   显示降级为 session executor 并在加载报告与返回值里标 `session-fallback`。
3. DoD（全部活体，证据取自加载报告 / 会话日志 / 证据日志，不采信模型自述）：
   - 子会话 id ≠ 父会话 id；
   - 子会话真的写了文件（证据里有它的 `write` 调用）；
   - `applyResult` 收到的是子会话的结果，父会话没有替它写；
   - 子会话在飞期间父会话工具仍可用（不自锁）。
4. 回滚：适配器开关 `execution.native_child_dispatch`，默认 `false`；先关着上线，实测通过再默认开。

## 9. 修订（2026-10-05，两轮活体验收之后）

- **深度上限：由「写死 1」改为「调用方深度 + 1」。** 写死 1 的实测后果是：由**深度 1 的会话**发起
  派遣（子 agent、Team 成员驱动 GAC 时就是这样），宿主回 `subagent depth 2 exceeds maxDepth 1`，
  子会话建不起来——写死的上限只对「调用方是根会话」成立。现在上限按调用方深度算：深度取会话头的
  `delegationDepth`（权威且单调）与 `AgentOptions.subagentDepth`（只能加深）里更深的一个，读不出来
  就**不带**这个字段、交给宿主自己的配置上限，而不是猜一个数字。§3 的意图（每次派遣只允许再开一层）
  不变。
- **产出契约必须是标准 JSON Schema。** 工具创作 DSL 里把 `required` 放进属性内部的写法
  （`{ type: 'string', required: true }`）被宿主拒绝：`unsupported JSON schema:
  schema.properties.status.required is not supported on type "string"`，而且这次拒绝发生在**子会话
  创建之前**——`advance` 只回一条 Error，节点停在 pending。同一个形状在四个工具的产出契约里都用着
  且都正常（那条路径是 DSL，会接受它），所以这个差别只有活体才看得见。
- **执行者抛错要按失败登记。** 此前异常一路穿到工具层，`advance` 回一条裸 Error、节点停在 pending、
  没有 dispatch_id、也没有失败记录。现在 `invokeNode` 把执行者异常登记为 `failed` 并把原因留在返回里
  （实测：`classification: accepted`、`action: repair`、节点转 failed）。

## 10. 阶段 1 的活体验收结论（2026-10-05，第三轮）：通过

四条 DoD 都有可追溯证据，且证据取自**运行时**（任务记录 / 证据日志），不采信模型自述：

| DoD | 证据 |
| --- | --- |
| 子会话 id ≠ 父会话 id | 任务记录 `REQ-CHILD-3` 的 `last_result_ref = "child-session:c0cc72e2-2d7b-4073-9f49-d4ba25639f7a"`；发起派遣的会话 id 是 `e159f5f9-0c74-44f0-8a5c-396e924cff1c` |
| 子会话真的写了文件 | 证据日志里那条 `write` 的 `session_id` 是子会话 `c0cc72e2-…`（`operation: create`、`before: null`），文件内容写着它自己的会话 id |
| 结果回到 `applyResult` | 父侧权威状态：`dispatched → reported(completed, classification: accepted)`、`attempt: 1`、`action: complete_task`；`advance` 返回「节点 T1 由 child:spawn 执行完成」 |
| 父会话不自锁 | 派遣期间与之后父会话的 `pwsh` / `write` 都正常（`parent-alive-3` 与它自己的对照件） |

三轮失败、三次都**只有活体看得见**（单测全绿）：产出契约必须是标准 JSON Schema；执行者抛错要按
失败登记；深度上限要按调用方深度算。三条都已修并各自留了测试。

### 残留现象（阶段 2 的输入，不要当成已解决）

1. **子会话继承了 GAC 自己。** 子会话里也有 `gac_*` 工具与 `gac:protocol` 提示段，于是它会自己声明
   作用域（证据里能看到它用自己的会话 id 取得 `.dsh/gac/local/` 的写占用）、并试着回报它那一侧的
   派遣；它自己的 `structured_output` 甚至写着「本次派遣 A1 的回报被运行时判为 stale，T1 现在停在
   blocked」，而父侧权威状态是 accepted / completed / 只有一次 attempt。**父侧没有被污染**，但
   「子会话能不能碰父会话的协调状态」不该靠运气——阶段 2 的角色工具面要显式排除 `gac_task` /
   `gac_scope` 这类父会话协调工具。
2. **返回文本里没有子会话 id。** `advance` 只说「由 child:spawn 执行完成」，`stopReason` 与产物清单
   也没渲染出来；可追溯性只存在于任务记录的 `result_ref` 与证据日志里，模型看不到。这与早先
   「派遣身份要写进返回文本」是同一类纸面缺陷。
3. **代码默认保持关。** `execution.native_child_dispatch` 的代码默认仍是 `false`（本工程自己的适配器
   已打开，用于继续实测）。理由就是第 1 条：在子会话的工具面被收窄之前，默认打开会让每个子会话都
   能碰父会话的协调状态。

## 11. 阶段 2 的活体验收结论（2026-10-05）：通过

验的是「只读角色也跑独立会话，而且它**模型面清单里根本没有 `write`/`edit`**」。证据取自**会话日志**，
不采信模型自述：

| 要验的 | 证据 |
| --- | --- |
| 独立会话 | 子会话头逐字：`{"id":"cd10da3a-…","parentSession":"d0c53b75-…","isSeeded":false,"origin":"subagent","delegationDepth":2,"agentPreset":"standard"}` |
| **模型面清单里没有写入工具** | 会话日志里 `request/header.data.header.tools`：父会话 43 个（含 `write`、`edit`），子会话 35 个（**`write` 与 `edit` 都不在**） |
| 子会话自己干活 | 该会话自签 7 条证据（glob/grep/read/pwsh/structured_output），**`write` 证据 0 条**；它读文件数出的答案与源码逐字一致 |
| 结果回父会话 | 任务记录 `last_result_ref = "child-session:cd10da3a-…"`、节点 `completed`、`attempt: 1` |
| 可追溯信息进返回文本 | `advance` 返回里出现「子会话 cd10da3a-…。」（§10 残留 2 已收） |

### 残留（如实记，不当作已解决）

1. **`subagent` 仍在子会话的清单里（8 个协调/委派名单里点掉了 7 个）。** 原因与「角色收权摘不掉 Team
   工具」同源：`subagent` 是 agent **自己那一层**注册的——既不在父会话的可收集合里（于是我们的名单
   取交集时把它滤掉了），也不受 `restrict` 管辖。而 GAC 传的 `maxDepth` 只约束**GAC 自己的派遣**，
   不约束子会话直接用 `subagent` 工具再开一层；那一步的上限归宿主自己的服务级配置。
   同一类还在清单里的有 `spawn_teammate`、`team_task_*`、`send_message`。
   **可能的修法**（未做，需要先量出竞态窗口）：`start()` 返回子会话 id 之后立刻给那个 id 登记一条
   角色收权，让 `tools/pre-execute` 守卫按会话拒掉这些名字——代价是子会话的首个调用可能跑在登记
   之前。
2. **子会话里仍有 `gac:protocol` 提示段，但已经没有 `gac_*` 工具**（五个都被点掉了）。提示段里提到
   「用 gac_evidence 查证据 id」，对一个手里没有该工具的会话是多余的；阶段 3 若要顺手，就在子会话的
   `persona` 里说清「协调类工具不在你手里，完成后按结构汇报」。

## 12. 阶段 3 的活体验收结论（2026-10-05）：A 成立、B 限于「启动时」、流程走到收口门禁

场景：一次真实的 `high_risk_task`（`REQ-HR-1`，节点 D1 验证方案设计 / I1 实现 / V1 独立验证 / R1 独立复核），
先按门禁顺序登记验证计划（`plan-82a1446a`）与冻结接口契约（`contract-781ec625`），再逐批派遣。

**A. 真并发：成立。** 同一批里 D1 与 I1 各跑一个真子会话：

| 观测 | 数值 |
| --- | --- |
| 两个子会话建立时刻 | 20:54:24.251 与 20:54:24.253（**相差 2 ms**） |
| `turn/start` | 相差 67 ms（I1 略早） |
| 活跃区间 | I1（12:54:31.398Z–12:54:50.575Z）**完整嵌套**在 D1（12:54:29.159Z–12:55:56.180Z）之内，重叠约 19.2 秒 |
| 派遣身份 | `REQ-HR-1-D1-A1` 与 `REQ-HR-1-I1-A1`，各自 reported accepted |

「逻辑并行 = 实际并行」现在有实测支撑——而这一条能成立，靠的是本次一并修掉的**实现侧串行循环**
（`f35fa8d`：`for … await` 改成先 `Promise.all` 同时起、再按批次顺序收结果）。此前它是伪并行，
且**不是平台限制**。

**B. Verification Design 盲区：启动时成立，但不等于「全程看不到」。** D1 的派遣提示（352 字符）与启动
上下文里对 `hr-impl`、`实现产物` **零命中**；`hr-impl.txt` 在 12:54:38 才被创建，晚于 D1 启动 14 秒。
**但 D1 在 12:55:06 自己把实现产物读了过来**（先读共享证据日志，再 `read` 那个文件）。所以准确表述是：
**启动时没有被推入任何实现信息**（提示词、上下文、依赖三者都不含），而**它完全可以自己去捞**——
`read`/`grep`/`glob` 对它都是开的。

→ §14（设计与实现并发）与 §15（设计盲区）在字面上有张力：两者同时成立要求设计节点**在实现产物存在
期间也读不到它**。可用方向有二：给设计节点一个**无工具面**（只靠提示词里的需求与验收标准推理），
或等平台提供**路径级读限制**。这属于新机制，不在本 ADR 已批准范围内，列为候选而不是已解决。

**C. 流程走到收口门禁。** D1/I1/V1/R1 四个节点全部 completed（四个子会话 id 均已记录），独立复核报告
登记成功（`review-853bd37a`，六问齐备、五个维度都有结论）；两次 `complete` 都被**证据门禁**如实拒绝，
缺的是每条用例的执行结论与证据引用。**DAG 完成 ≠ 可以收口**，门禁按设计工作。

**顺带修掉一处只有活体才看得见的误报**：没交验证载荷与交的载荷对不上计划，此前共用 `PLAN_MUTATED`，
于是「压根没带 `verification`」被报成「报告对应的不是当前计划（报告写的是 undefined）」——而盘上计划
身份核对其实是 matches，拒因把读的人引向「有人改过计划」。现在分开为 `GAC_VERIFICATION_PAYLOAD_MISSING`，
消息直接说缺什么。

## 13. 事故与修复：把插件自有事件写进会话日志（2026-10-05）

**症状**：用户报告「子智能体的历史记录全部都显示不出来，点进去全报错」。这不是宿主的问题，是本插件
写进那些日志的数据让它们读不回来了。

**机理**：会话日志的事件词表由宿主**构建期生成**（`dsh-session` 的 `KNOWN_SESSION_EVENT_TYPES`），
外部插件的类型按构造就不在其中；而 `Session.append(type, data, ...opts)` 只把 `sourceEventSeqs` 与
`surfaceOp` 放进日志，**没有任何途径**给一条事件打上 `ignorable` 标记。持久化层读回日志时因此整份
拒读（`dsh-session-persistence/lib/index.js` 的 `validateStoredEvents`）：

```text
session "…" contains event type "gac/…" (seq N) unknown to this harness and not marked ignorable;
refusing to interpret the log — it was likely written by a newer harness
```

原实现每次 GAC 工具调用后 `session.append('gac/…', …)`，并为每个类型注册消息投影，目的是「让 GAC
事件出现在对话历史里」。**把「出现在历史里」当成了纯收益，漏掉了读回日志的人未必装着这个插件**
——而本插件的默认状态恰恰是「不装」。更糟的是：拒读发生在读日志的时候，**把插件打开也救不回来**。

**损害范围**（扫描本工程的会话目录）：62 个会话日志里 23 个含 `gac/*` 记录、共 97 条，全部落在
「不认识且未标 `ignorable`」上。今天那些用过 GAC 工具的子会话与根会话都在其中。

**为什么当时近千条测试全绿**：没有任何一条断言过「我们往会话日志写了什么」——假 ctx 里的
`session.append` 是个空函数，谁也没看它被怎么调用。

**修复（三件）**：
1. `lib/gac-event-log.js`：审计事件改写进工程自己的追加文件 `.dsh/gac/events/events.jsonl`，一次
   工具调用一批、由运行时发号、形状仍过 `compileGacEvent`。
2. 删掉写会话日志与注册消息投影两条路径；`createGacProjection` 一并删除——它只能配合那条被删掉的
   路径使用，留着就是诱饵。
3. `scripts/repair-session-events.js`：给已写入的记录补 `ignorable` 标记。那是宿主为这种情况留的
   出口：记录作为**不参与重放**的日志项被保留，审计线索不丢、日志可正常读回。默认预演；`--apply`
   先备份、再原子替换，并把并发追加的新帧接回去（修活着的会话时不会丢掉最新对话）。

**回归钉子**：`test/session-log-integrity.test.js` 用一个记录每次 `append` 的假 ctx，断言它**始终为
空**、且插件不注册任何消息投影。突变检查过：把 `append` 加回去，这条测试立刻红。

**执行结果**：预演 23 个会话 / 97 条记录 → `--apply` 修完 → 逐帧复查为 0 个解不开的帧、97 条
`gac/*` 记录仍在、0 条「不认识且未标 `ignorable`」；本会话（活着的那个，1321 帧 / 4473 条记录）
尾部完整，23 份备份留在原地。

**留下的教训**（已写进 `AGENTS.md` §0 的硬性条目）：审计与可观测性写在**工程自己的文件**里，不要
写进宿主拥有的持久化格式——对那种格式，外部插件只有「读」的资格。

## 14. 阶段 4 之一：子会话的授权绑定（2026-10-05，已活体验收）

**缺口**：阶段 2 把 `gac_*` 从子会话工具面里收掉时，漏掉了运行时那一侧的绑定。全仓库 `declareScope`
只从 `gac_scope` 工具调用，而守卫在「这个会话没有声明」时返回 allow——于是**严格写作用域管不到子会话
的写入**，约束它的只有 persona 里那句措辞。

**收口方式（设计要点）**：不在守卫旁边再挂一张表，而是**运行时代替子会话往同一张作用域注册表声明
一次**（`lib/child-binding.js`）。判定逻辑（PTC 外层放行、shell 整体拒绝、运行时工具放行、未知工具
失败即拒、按路径查作用域）本来就在守卫里，两条来源因此走同一条判定，差别只在 `origin` 与拒因里的
身份字段。声明随之可携带 `dispatch_id` / `attempt` / `child_session_id` / `parent_session_id` / `role`，
越界与 shell 被拒时五个身份一起进拒因。

**只绑写者**：空 `write_scope` 不绑。因为「生效中的写作用域会整体拒绝 shell」，把空 scope 绑给验证者
会顺手拿走它的 shell，而独立验证要靠 shell 逐条执行计划用例。**代价是实测过的**：写者子会话在作用域
生效期间确实失去 `pwsh`（活体验收里验证者亲眼看到自己的 shell 调用被拒），builder 必须走结构化
`write`/`edit`。

**释放与隔离**都以 `dispatch_id` 为界：旧 attempt 的迟到释放不得动摇新 attempt 的绑定，同一个会话被
重新绑定之后旧 dispatch 的释放什么也不动。

**活体验收（`REQ-SCOPE-2`，隔离子 agent）**：子会话 `46dba699-…`；返回文本逐字含
`已绑定写作用域 [.dsh/gac/local/scope2-allowed.txt]`；边界内写入落盘（内容 `ok`）；越界写被
`GAC_WRITE_SCOPE_DENIED` 逐字拒绝且 `Test-Path` 为 `False`（盘上确实不存在）；`structured_output`
被接收 → T1 `completed` / `accepted`；父会话 `still-alive`。

**同轮抓到的两处缺陷（都已修）**：
1. **子会话的回报通道被自己的作用域拒掉**：`structured_output` 不在分类表里 → 落进 `unknown` →
   `GAC_UNGUARDABLE_WRITE_DENIED`，于是子会话把两件事都做对了却被判 `failed`。修法是把
   `structured_output` 与 `todo_write` 归进运行时平面（都碰不到产品文件），**「失败即拒」规则不动**。
   教训写进 `lib/tool-targets.js`：fail-closed 分类表意味着**子会话要用的每一个非写入类工具都必须被
   显式归类**——这一条以前没人做过，因为以前没有工具在作用域下跑过。
2. **提示段落主动误导子会话**：它读到「先用 `gac_project` 声明模式、用 `gac_scope` 声明路径」，可
   授权已由派遣者绑定、那两个工具也不在它手里。现在子会话分支**替换**那两段；判据取**宿主会话头**
   （`parentSession` / `origin: 'subagent'`）而不是取绑定——只读子会话按设计不绑作用域，可它同样
   需要这套话。

**一条如实记下的非保证（AC27）**：绑定发生在 `start()` 返回之后。契约上**不存在**「子会话首个工具
调用之前」的钩子，所以它是「实际窗口可忽略」（子会话的首个工具调用至少要等一次模型往返）而不是
硬保证。要变成硬保证需要一个更早的限制接缝，那不在本 ADR 已批准的范围内。

## 15. 阶段 4 之二：语义产物由运行时登记（2026-10-06，已活体验收）

**缺口**：真实 `REQ-HR-1` 的四个节点全部 `completed`，而收口两次被拒——验证计划、逐条用例结论与
复核报告都要**父会话额外调用 GAC 工具手工登记**（复核那次甚至是父会话重新读证据再补登的）。那是
错误的职责边界：**子会话负责产生认知结果，运行时负责校验、持久化与推进状态**，而不是「子会话写
一段散文、父会话再解释成产物」。同时，`{status, summary, artifacts}` 这一个万能契约只够做**传输**，
带不回语义产物；而 `required_capabilities` 只决定「谁来做」，决定不了「做什么、产物是什么」。

**收口方式**：节点显式声明 `role`（`implementation` / `verification_design` / `verification_execution`
/ `review`），执行者按角色挑产出契约、只**运输**语义产物（`semantic`，含 `child_session_id`），
校验与落盘在 `gac_task` 那一层——只有那里同时握着任务存储、门禁与证据日志。四条链因此闭合：

- **设计 → 计划**：设计节点是**计划的作者**，计划门禁只对**显式声明**该角色的节点豁免（缺省推断
  永远不会给出它——那条豁免不能靠推断拿到），交回的方案由运行时编译、冻结、落盘，不合法当场判失败。
- **验证 → 报告**：逐条结论由运行时先核对**计划身份**（对不上当场判失败，不一路滑到收口），再把
  证据引用解析成真实签发过的号；登记与收口**共用同一套** `evaluateVerification`。
- **复核 → 报告**：六问与五维由 `compileReviewReport` 校验，`reviewed_plan_id` 由运行时盖
  （「登记这一刻的冻结计划是哪个」是可观察事实，不交给复核者自报）。
- **收口**：`evidence.verification` 没交时自动取运行时登记的那一份。

**证据引用为什么是 `self:<n>` 而不是 `ev-NNNN`**：子会话看不到运行时签发的号（`gac_evidence` 已从
它的工具面收掉），但它数得清自己调用了几次；而「这个号是不是运行时发过的」只有运行时知道。于是
子会话报序号、运行时去自己的账本取号，解析不出来就**不登记**（那条用例缺证据，收口会拒）——
伪造一份引用放过去比拒绝更糟。复核报告的引用还允许 `self:<n>#明细`，明细原样保留。

**四轮活体验收**（每轮都由隔离子 agent 在真实会话里驱动，`REQ-HR-2/3/4/5`）：

| 轮次 | 走到哪 | 抓到的缺陷 |
| --- | --- | --- |
| 1（`REQ-HR-2`） | 设计节点自动冻计划成功；验证节点 `failed` | 提示词把计划 id 渲染成「(见盘上)」（id 是内容寻址算出来的，不在计划对象里）；子会话漏报三条用例；两条用例复用同一份证据（`ev-1100`） |
| 2（`REQ-HR-3`） | 验证节点完成并自动登记报告（`ev-1217/1221/1222/1223`）；复核节点 `failed` | 复核产出里的**传输字段** `status` 被直接丢给 `compileReviewReport`，整份报告判 MALFORMED |
| 3（`REQ-HR-4`） | 四个节点全 `completed`、三份产物齐全；收口被拒 | 复核报告的 `evidence` 要求运行时签发的号，而提示词让它写 `self:<n>`——**复核路径没有解析**，每条引用都被判「不是运行时发过的号」，收口被挡；另有 `grill confirm` 传错字段名（`criteria`）静默冻成 0 条验收标准 |
| 4（`REQ-HR-5`） | **收口成功（`status: completed`）** | —— |

**第四轮的验收结论**（`REQ-HR-5`）：四个节点全部 `completed`；计划由设计节点产出并被运行时冻结
（`plan-778ae0d5`，4 条用例、覆盖 `AC1`/`AC2`、两条反例都写明 `expect_failure`）；验证报告由验证
节点产出并被登记（四条**互不相同**的真实证据 `ev-1486/1487/1490/1493`）；复核报告由复核节点产出
并被登记（`blocking_issues: []`、六问齐备、18 条引用、`reviewed_plan_id` 由运行时盖）；收口返回
逐字是「任务 REQ-HR-5 已收口。」。**父会话零语义补写**：`create → grill×4 → contract → advance×3
→ status → complete`，其中 `plan` 未调用、`review` 未调用、`complete` 未带 `verification`——
这一条不是转述，是从运行时**自己的证据账本**里逐个会话数出来的。

**留下的教训**：两个契约（子会话产出契约与产物编译器）各有各的字段表，**谁都不该把超集交给对方**；
运行时按白名单挑字段，而不是逐个剔除——将来产出契约再加字段时才不会再撞一次。

### 15.1 三份失败现场（保留，不要清理）

前三轮的失败不是「跑坏了要重来」，它们是**每个修复所对应的唯一物证**：单测断言的是修好之后的行为，
只有盘上这些记录留着当时那条路径真的断在哪里。它们都在 gitignore 覆盖的运行时状态里
（`.dsh/gac/**`），所以本 ADR 是它们的长期载体；**若哪天清理运行时状态，请先确认本节信息完整**。

| 现场 | 停在哪 | 盘上留下什么 |
| --- | --- | --- |
| `REQ-HR-2` | 任务 `failed`；D1/I1 `completed`、**V1 `failed`**、R1 `pending` | 计划、契约；**没有**验证报告（报告被拒未登记） |
| `REQ-HR-3` | 任务 `failed`；D1/I1/V1 `completed`、**R1 `failed`** | 计划、验证报告（4 条真实证据）、访谈记录、契约；**没有**复核报告 |
| `REQ-HR-4` | 任务 `in_progress`；**四个节点全部 `completed`**，五份产物齐全 | 计划、验证报告、复核报告（含 1 条阻塞问题）、访谈记录、契约——**唯一缺的是收口本身** |

三处逐字拒因（它们分别是三个修复的触发者）：

- `REQ-HR-2` 的验证报告：`验证报告被拒：缺少已执行证据的用例：C2, C3, C6；同一份证据被多条用例共用，不构成独立证据：ev-1100（C4、C7）。`
  同轮的 `advance` 文本第一次带上失败分支的可追溯信息：`节点 V1 由 child:spawn执行结束（结论 failed）。子会话 93e18822-…`
- `REQ-HR-3` 的复核报告：`复核报告被拒：复核报告带有未声明的字段：status。`
- `REQ-HR-4` 的收口：`任务 REQ-HR-4 的独立复核未通过，不能收口：复核留下了 1 个阻塞问题：复核子会话的证据引用形式与收口核对口径不一致……这些引用不是运行时发出过的证据号：self:14# …`（`GAC_REVIEW_EVIDENCE_NOT_FROM_RUNTIME`）

`REQ-HR-4` 那一份特别值得留着：**四个节点全绿、三份产物齐全、父会话零补写，而收口仍然被拒**——
它说明这条链上「每个局部都做对了」不等于「整体成立」，而拦住它的恰恰是运行时自己的核对（复核报告
的引用必须来自运行时签发的号）。也正因为它拒得对，修法只能是让运行时解析 `self:<n>`，而不是放宽
门禁。

## 16. 阶段 4 之三：原生子会话的模型路由（2026-10-06）

**缺口**：适配器里原有 `execution.provider_routes`，按**执行者名**作键，只作用于进程内执行者。而
原生子会话路径上**只有一个执行者**（`child:spawn`）覆盖全部节点——按执行者名根本区分不出「验证者
跑在另一个模型上」，于是「独立验证跑在独立模型上」在原生路径上做不到（README 里那句「验证者跑在
另一个模型上是配置而不是约定」只对进程内那条路成立）。

**收口方式**：新增 `execution.role_routes`，按**语义角色**作键（`*` 是所有角色的缺省），运行时把它
翻成宿主的 `SubagentStartRequest.agentOptions`（`provider` / `model` / `reasoningEffort` /
`maxTokens`）。三条设计决定：

1. **两套键空间不混用**：`provider_routes` 管进程内执行者（按名字），`role_routes` 管原生子会话
   （按角色）。混用会让「同一个执行者名」在两处含义不同，而那正是静默失效的温床。
2. **无路由 ≠ 空路由**：没有匹配到就**不传** `agentOptions`（子会话继承父会话的 provider/模型/推理
   档位）；传一个空对象会把父会话的模型一起清掉。这条在代码与测试里都单独钉住。
3. **名字必须翻**：适配器是 JSON 用 snake_case（`reasoning_effort`、`max_tokens`），宿主收 camelCase
   （`reasoningEffort`、`maxTokens`）。宿主对多余的键**不报错**，所以翻错的表现是「配置写了但一点
   效果都没有」——突变检查（把 `reasoningEffort` 改回 `reasoning_effort`）会让 3 条测试变红。
4. **路由要看得见**：每次派遣的实际路由写进 `advance` 的返回文本（`；路由 provider/model`）。配错了
   模型、或某个角色悄悄继承回父会话，只能从这里发现。

**角色名的词表只有一处**（`lib/coordinator.js` 的 `NODE_ROLES`），适配器校验直接引用它：拼错的角色名
在**读适配器时**就被拒，而不是派遣时静默不生效。

**一次自我纠正**：写这一节时顺手想给适配器缓存加 mtime 校验（「改了适配器不重载插件就不生效」看着
像缺陷），但那会撞掉两条**明确写着旧契约**的测试（「缓存成功的一次加载」「缓存不存在」）。想清楚后
撤回：那两条测试编码的是一个有意的决定——**策略在同一会话里必须稳定**，中途换适配器会让跑着的任务
脚下换规则；而「改了没生效」是可发现的（返回文本里的路由行会显示实际生效的那一条）。所以这条不修，
改为写进 README 的操作说明。

**活体验收（两轮，都由隔离子 agent 驱动）**：

| 轮次 | 配置 | 结果 |
| --- | --- | --- |
| 1（`REQ-ROUTE-1/2`） | `*` → `provider: "spawn"`；`review` → `no-such-provider-xyz` | **两个方向都被宿主拒**：`no adapter registered for provider "spawn"` 与 `…"no-such-provider-xyz"`（`NO_ADAPTER`）。子会话的 `request/header` 里逐字出现被路由的那个值——**这证明路由确实一路走到了宿主的子会话创建请求**，也同时证明我配错了语义 |
| 2（`REQ-ROUTE-3`） | `*` → `provider: "opencode-go"`（本机真实的模型 provider） | 节点 `completed`；返回文本逐字含 `；路由 opencode-go；`；产物落盘；子会话 `83adf160` **自己的会话日志**里模型请求头是 `provider = opencode-go`——宿主侧事实闭合 |

**第一轮那个错必须记下来**：`agentOptions.provider` 是**模型 provider**（已注册的模型适配器），而
`spawn` 是**派遣接缝名**（`ctx.subagents.start()` 的第一个参数）。两个词都叫 provider，我混用了，
写进了 README 示例，也被活体验收当场抓住。这正是这类机制最容易出的错：**配错不会报「配置无效」，
而是让子会话起不来**——所以修法不是放宽校验，而是把语义写清楚，并让返回文本带上实际路由与失败原因。

**同轮补上的可追溯性**：第一轮里失败原因（`NO_ADAPTER`）只活在子会话日志里，`advance` 返回文本只
说「结论 failed」。现在子会话没回结构化产出时，宿主的 `diagnostic` 会进返回文本——失败时父会话最
需要的就是原因，而不是一个 id。

## 17. 阶段 4 之四：witness 与 PTC 的收口决定（2026-10-06）

**这两条卡在同一个地方**：`workspaceChanges`（工作区观测源）与 PTC 运行时（`run_code`）都由
**没被装进本机 profile 的包**提供——包本身在桌面安装里有，但既不在被提升的 junction 集合里
（`~/.dsh/profiles/node_modules/@deepseek-ai/*`），也没有被任何已加载的插件引用。

**决定：不把这两个包装进 profile。** 理由不是技术难度，而是**代价不对称**：

- 装 junction 只是第一步。要让服务真的存在，还得把提供者插件写进 `cordis.yml` 并重载宿主——那会在
  **每一个会话**的工具面里多出 `run_code`（模型自写代码执行）与一套工作区观测插件，那是**产品面
  变更**，不是「为了一次验收临时开一下」。
- 换来的是一条验收结论；付出的是用户宿主的能力边界被改动。为一个测试结论去动能力边界，方向反了。

**改成做能做的两件事，并把剩余风险写清楚**：

1. **接线层集成测试**（已有的 `test/workspace-witness.test.js`）：它用**真实的 `apply()`** 注入一个
   假的 `workspaceChanges` 服务，再触发 `workspace/changes` 会话事件，断言证据落盘与越界分类。
   也就是说这一层不是「只有单测」——之前 CUTOVER 里那句话写轻了，本次一并改正。
2. **对着真包的契约核实**（本次新增，只读桌面安装里的类型声明，`0.2.0-rc.2`）：
   - **witness**：服务接口是 `WorkspaceChanges.summary(sessionId, seq)`——**两个参数**。包里另有一个
     单参数的 `summary(seq)`，那是**内部 recorder**；只按它写会取不到摘要，于是 witness 证据永远
     不落，而假件测试跟着错的签名写、测不出来。摘要与文件字段名逐字段比对一致
     （`{turn, cwd, files, total, added, deleted}` / `{path, display, added, deleted, binary?: true,
     oversized?: true}`；`binary`/`oversized` 是可选真值标记，不是 `kind` 判别联合——后者是
     `WorkspaceFileDiff` 的形状，容易看串）。核实结论写进了 `lib/workspace-witness.js` 的模块头。
   - **PTC**：工具名 `run_code` 在多处被引用；`ToolExecution.parent` 的注释逐字写着「PTC mode sets
     this on SDK sub-dispatches」与「under `mode: 'ptc'`, only calls WITH a parent may execute a
     native tool name — a model-direct call (no parent) is denied as `UNKNOWN_TOOL` before the policy
     pipeline」。这正是守卫那套「外层传输放行、内层调用逐次过 `tools/pre-execute`」所依赖的内核事实。

**仍未闭合的**：真机活体（真实服务/真实 PTC 运行时在场时的端到端行为）。它需要上面那套 profile
变更。若要启用，步骤是：给 `~/.dsh/profiles/node_modules/@deepseek-ai/` 加两个 junction（指向桌面
安装），把提供者插件加进 `cordis.yml`，重载宿主，然后复跑一次 `workspace/changes` 观测与一次
PTC 内层写入。**在没有做这些之前，任何「witness/PTC 已验证」的说法都是不成立的**——本节只声明
契约核实通过，不声明活体验收通过。

## 18. 阶段 4 之五：审计视图（事件溯源的实用形态，2026-10-06）

**「事件溯源/记忆」这一阶段要回答什么，先得说清楚。** 原计划里它写作「事件溯源与记忆」，两种做法
差别很大：**跨任务的记忆沉淀**（把历次失败模式攒起来喂给下一次），或**审计查询面**（把一次任务
发生过什么、凭什么收口讲清楚）。**选后者**，理由不是省事：前者没有具体消费者，只会得到第二份会
漂移的真相源——而本仓库反复吃亏的正是「两处各自维护同一件事」；后者有明确的读者（收口之后复盘的人
与模型自己），而且**真相已经在盘上**：任务记录、需求冻结、契约、验证计划、验证报告、复核报告，
加上 `.dsh/gac/events/events.jsonl` 那份只追加的审计日志。

**收口方式**：`gac_task action: "audit"`，**纯派生、只读、不新增存储**。`lib/task-audit.js` 是纯函数
（给它已经读出来的东西），工具层只做连接（读六份产物 + 按 `task_id` 筛事件 + 取运行时签发过的证据号）。
它做三件在这一层才看得见的事：

1. **拼时间线**：日志本身只有一串事件，没有「任务视图」；派遣与回报的语义要在这里还原。
2. **核对产物之间的身份**：验证报告与复核报告写的是不是**当前**那份计划。单看任何一份产物都发现不了
   ——每一份自己都是合法的，配在一起才是错的（内容寻址的 `plan_id` 让这件事可判）。
3. **把缺口说出来**：缺什么、什么没冻、哪条引用的证据号运行时从未签发过（收口之后仍能查出伪造引用）。

**两条口径**：其一，**一个根因只报一次**——没有计划时不再重复计「缺验证报告」，因为那是后果不是独立
缺口；反之计划没了而报告还在时，那两份报告会被标成「对不上当前计划」，因为那正是事实。其二，**只读
且不判对错**：审计不改任何状态，也不回答「这次做得对不对」（那是复核与门禁的事）。

**刻意没做的**：跨任务的历史沉淀。它需要一个具体的问题来定义「什么算同类失败、沉淀成什么形状」，
而目前没有这样的消费者。**留在这里而不是悄悄做掉**，是因为「记忆」这种东西一旦做成第二份真相源，
后面每一个门禁都要回答「以哪一份为准」。

## 19. 能力面收缩：Witness 升为生产纵深防御层；PTC 的收缩**已撤回**（2026-10-06）

**决定**：把两个待验能力**拆开**处理——它们不是同一类东西。

| | Witness（工作区观测） | PTC（`run_code`） |
| --- | --- | --- |
| 它是什么 | **纵深防御层**：事前拦截够不着的那一类落盘（shell 重定向、生成器、外部进程、间接写入）的事后记录 | **执行便利**：模型写一段代码批量调用工具 |
| 是不是权限/验证/证据/隔离原语 | 是观测原语（证据的一部分） | **都不是** |
| 缺席意味着什么 | 「没有越界写入」这句话无从成立 → **降级要可见** | 正常：GAC 仍然完整、安全、正确地工作 → **不产生告警** |
| 定位 | **生产能力契约里的必需项**（**已在日常 profile 活体验证**，证据 `ev-1820`） | **已装载，非必需**；不作为切旧运行时的门槛 |

**为什么 Witness 不能只活在验收 profile**：那意味着验收时验的是运行时 A、日常跑的是运行时 B
（「Do not validate one runtime and operate another」）。**2026-10-06 的结论是：它本来就在日常 profile 里**——
见下面的更正。

### 19.1 撤回：PTC 的「明确不支持」收缩

**本轮曾做**：把 `run_code` 归类为「本 profile 不支持的传输工具」，守卫对它**明确拒绝**
（`GAC_PTC_UNSUPPORTED_BY_PROFILE`），并删掉「放行外层传输 + 内层子调用按名字受管」那套逻辑
（`nested` 参数、两条内层分支、`knownTools().ptc` 与那组测试）。

**为什么撤回**：那个改动的**前提是假的**。前提写的是「日常 profile 不装 PTC 运行时，`run_code`
永远不会出现」，而事实是：

```text
dsh-base/cordis.patch.yml:390-391
- id: ptc-runtime
  name: '@deepseek-ai/dsh-ptc-runtime-node'
- id: workflow-ptc
  name: '@deepseek-ai/dsh-workflow-ptc'
```

**没有 `disabled:`**——PTC 运行时在**每一个含 `dsh-base` 的 profile 里都是装载的**。`run_code` 不在
模型工具面里，是因为它**只在 PTC 模式下才被呈现**，不是因为不存在。于是那个改动会把**PTC 模式下
声明了写作用域的活能力**从可用改成不可用：那不是收缩死代码，是打断活能力。

**撤回后的状态**：守卫恢复「放行外层传输（它自己不碰文件）、内层子调用各自按名字受管（`write` 查
作用域、`pwsh` 按 shell 拒、未知工具失败即拒绝）」。**仍然成立的结论保留**：PTC 是执行便利、不是权限
原语，**不作为切旧运行时的门槛**；缺席时**不产生**降级告警。

**撤回后的行为已活体验收（2026-10-06，PTC 呈现模式）**：放行外层传输、内层子调用按名字受管，这条不只是
推理。声明写作用域之后，内层 `write` 写范围内文件放行、写范围外文件被 `GAC_WRITE_SCOPE_DENIED` 拒（该文件
盘上确实不存在）、内层 `pwsh` 被 `GAC_SHELL_DENIED_UNDER_SCOPE` 拒，而**外层那段程序越过这两次拒绝照常
跑完**；释放作用域后 shell 立刻恢复可用。也就是说，撤回救回的正是这条实测下来确实能跑的能力。逐字证据与
自包含配方见 `docs/PTC-LIVE-PROBE.md` 与 `docs/CUTOVER.md` §4。

**这次错误的形状值得记下来**（它是本节最有价值的部分）：我判「能力在不在」用的是**解析层**——
profile 自己的 `package.json` 里有没有它、提升的 junction 集合里有没有它。而正确的判据是**已加载树**：
服务在不在（加载报告的 `witness-seam` 那一行）、事件来不来（`workspace/changes` 有没有被追加）。
两者给出的是**相反**答案，而且解析层的答案还自带一堆看似合理的旁证（「profile 的依赖列表里确实没有
它」）。同一个错误在**同一轮里犯了两次**：`workspace-changes` 与 `ptc-runtime` 都不在 profile 自己的
依赖里，却都因为某个 bundle 的 patch 插入了那一行而**一直在场**。判据已写进 README 的生产能力契约。

**另有一条次要结论保留**：`roleRevokedToolNames` 只跳过 READ / RUNTIME /（可选）SHELL，**`unknown`
是进收权表的**。所以若哪天真的要把 `run_code` 从分类里删掉，在装了 PTC 的 profile 里会发生：

```text
run_code → unknown → 进收权表 → 那条 !== PTC 的护栏也一起没了
→ restrict 被点名 run_code → 宿主抛「cannot name reserved PTC mode presentation transport」
→ 子会话创建失败
```

也就是说「删干净」会给将来埋一颗爆在最难查处的雷；`lib/role-guard.js` 里那条把 `run_code` 排除出
`restrict` 名单的护栏要留着。

## 20. 生产能力契约的执行点：声明 → 核对 → 拒绝结论（2026-10-06）

**问题**：README 的「生产能力契约」是一张表，而**没有任何代码消费它**。本仓库在 `checkpoint` 那条上
已经吃过一次同样的亏（`AGENTS.md` §5 自己承认它「没有代码消费」）。只写在文档里的契约会与代码漂移，
而漂移的方向恰好是危险的那一侧：文档说「工作区观测是必需项」，代码里却没有任何地方在它缺席时说什么。

**决定**：把那张表变成三件可执行的事，各有一处代码：

| 环节 | 在哪里 | 它回答什么 |
| --- | --- | --- |
| 项目**声明** | 适配器 `execution.required_capabilities`（闭集 `lib/capabilities.js`） | 这个工程依赖哪些生产能力 |
| 环境**核对** | `lib/index.js` 第一次工具调用时逐项核对，写加载报告的 `capability-check` | 已加载树里到底给不给 |
| 收口**拒绝结论** | `lib/tool-task.js` 的 `complete` 门禁（`high_risk_task`） | 缺项时这个「通过」能不能成立 |

**为什么拒的是结论、不是工具**：观测缺席时，「没有越界写入」这句话**没有依据**——缺的是结论的凭据，
不是工具的能力。所以门禁落在收口这个动作上，并且**留一条显式豁免**（`capability_ack`）：一个永远收不了
口的高风险模式就是「把自己关在门外」的同一个形状，本仓库在 `gac_scope` 上已经踩过一次（那次是门禁
拒绝了唯一能释放作用域的工具）。豁免随任务记录落盘、随记录恢复、出现在 `gac_task action:"audit"` 的
链条里——**不留痕的豁免等于一次静默通过**。

**判「在不在」看已加载树，不看 profile 的 `package.json`**（§19 的教训）：核对读的是两个接缝的真实
状态，不是解析层能不能找到包。

**这一轮实现时踩到的两个坑，都留下了测试**：其一，`createTaskTool` 有一张**参数白名单**，新依赖没
加进去就被静默丢掉——与 `registerTools` 注释里记的 `roleGuard` 那次是同一类（那次丢了五个工具才发现），
而新写的门禁测试当场抓到了它。其二，适配器的 `execution` 是**逐字段重建**的，`required_capabilities`
没搬进去就等于声明被静默丢弃（「项目没声明」与「声明被丢了」在表现上一模一样）——与 `role` 当初在
序列化时丢掉是同一类，入口侧的核对测试抓到了它。两处都做了突变检查：去掉拒绝分支、或让归一化丢掉
声明，相关 10 条测试里 5 条立刻红。

## 21. 收口：语义角色工具面、委派封堵、默认策略（2026-10-08）

这一轮补的是**最后一步**：多 Agent 已经能自动工作，但「每个角色只能知道和做它该知道和该做的事」当时
不是由运行时保证的。三件事，按落地顺序：

**其一，工具面按语义角色给，不再从「写范围是否为空」推导。** 新增 `lib/role-tools.js`：每个角色一档，
判据只有一处——语义角色。原设计把「有没有声明写作用域」当成「能不能写」的判据，这在实现节点上是对的，
但**设计节点与验证执行的写范围都是空的，读取能力却必须相反**（一个必须什么都读不到，一个必须读得到
实现才能执行计划）。于是「空写范围 ⇒ 只收写入工具」这条推导把设计节点的 `read`/`grep`/`glob` 全部留了
下来——真实 `REQ-HR-5` 里设计子会话启动时确实没被推入实现信息，但它随后自己把 `hr5-artifact.txt` 读了
过来（推理里出现「3 bytes = ok\n likely」）。独立性不能靠提示词（工具还在，模型就仍有能力读），只能靠
**结构**。

**其二，收权分三层，缺一层都只是部分保证。** ① 创建窗口的 `toolFilter`：无竞态，但结构上**只收得到
继承来的工具**（父会话自己那层注册的名字不在子会话的可收集合里）；② `start()` 之后用**子会话自己的
视图**对账补收 + 一条单调守卫（`lib/child-surface.js`，注册在子会话 `agent.ctx` 上，只作用于它）；
③ 全局门禁按会话读角色兜底（`lib/plugin.js` 的 `childRoleFor`）。第 ② 层收不掉时如实降级成 `guard-only`
并记 `child-surface-unverified`——「没法确认」不写成「已经收掉」。

**其三，委派封堵与父会话协调类。** `subagent` / `subagent_fork` / `workflow` / `spawn_teammate` /
`send_message` / `team_task_*` 与 `gac_*` 在任何语义角色下都被拒，稳定码 `GAC_CHILD_DELEGATION_DENIED`，
拒因带 `child_session_id` / `task_id` / `node_id` / `role` / `tool`。编排权归 GAC，子会话只执行分配到的节点。

**一处旧归因被推翻（这是本节最该记住的一条）。** §12 与 `CUTOVER.md` §3 E2E-6 曾写：`subagent` 收不掉，
因为「它是 agent 自己那一层注册的，既不在可收集合里、也不受 `restrict` 管辖」，并进一步推断「收权落到的
作用域与模型面清单装配用的作用域不是同一个（疑似会话，未查明）」。**两个判断都错了**，对着内核源码
（`@deepseek-ai/dsh-tools` 的 `view` / `restrict` / `guard`）逐条核对后的事实是：

- `restrict` 只过滤该作用域**继承**来的工具（全局层 + 链上祖先层），**own 层注册的工具无条件保留**；
- 这条豁免是**刻意的**，内核注释写明理由：委派运行时把子会话的结构化产出工具注册进它自己的层，
  一份「点名子会话可用能力」的过滤器不该把它答话的机器一起剥掉；
- 所以 `subagent` 不是「收不掉」，而是**没被点名**——它确实在 `view(scope).restrictableNames` 里。

教训与 §19 那次同形：**判据要从真实接缝的读数来，不要从「我以为它不在那里」来**。同一次核对还确认了
另外两条：`restrict` **按名字拒绝 `run_code`**（保留名），所以 PTC 只能由守卫兜底；`restrict` 对不认识的
名字抛错，代价是整次收权归零——因此名单只能来自 `view(scope).restrictableNames`，不能猜。

**`native_child_dispatch` 的默认值翻转为开。** 当初不给默认值的三条理由（子会话工具面没收窄 / 子会话
写作用域未完成 / 语义结果未完成）都已关闭；默认关会让新纳管工程**静默退回主会话自我验证**，而这正是
本轮要消灭的那个失败方向。默认开**不等于**静默降级：接缝缺席时，高风险任务与含非实现节点的任务**阻塞**
（`GAC_CHILD_SEAM_UNAVAILABLE`，不由主会话代跑），只有「全是实现节点且非高风险」才显式降级成
`in_progress` 并说明原因；`direct_edit` 永远不起子会话。

**仍然没有证明的两件事，照实留在这里**：① 进程外 provider 拿不到 `localAgent`，第 ②③ 层在那条路径上
装不上——此时记 `child-surface-unavailable` 并按角色阻塞，**不宣称委派已被封堵**；② 「真实子会话呈现给
模型的那个工具面清单」还没有活体核对过（本轮验的是判据、收权与守卫的单测/集成，以及真实会话里已验证
的写作用域与语义产物链）。要闭掉第 ② 条需要开插件跑一次真实子会话并读它的 presented 名单。
